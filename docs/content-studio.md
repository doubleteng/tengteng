# Content Studio

Open https://teng-teng.org/admin/ . The footer's Manage link opens this editor.

Select a project, page-data file, publication, or update. The central preview uses the repository's actual Liquid templates and public stylesheets. Click content to select its field; double-click plain text to edit in place. The inspector provides rich text, image/video selection, and explicit block ordering. Switch between desktop and 390px phone widths. Use the carousel arrows to inspect each image.

Edits remain local drafts until **Review changes / Publish**. Reloading restores text drafts. Export/import provides a portable backup. Newly uploaded files stay in tab memory until published and must be reselected after a reload. Maximum upload is 20 MB; existing assets are never overwritten.

For first-time publishing, connect a fine-grained GitHub personal access token scoped only to `doubleteng/tengteng` with Contents read/write. The token stays in tab memory and is not written to storage, URLs, logs, or the repository. Refreshing disconnects it. Public content can be previewed and edited without connecting. The previous Pages CMS form is no longer the admin entry point.

## Preservation model

- Parse the exact original YAML and Markdown. No-op edits return the identical source.
- Update only the selected node's byte range. Do not rebuild a whole document from a form schema.
- Move/remove YAML sequence items as complete original source slices, preserving unknown nested fields. Explicit edits to flow-style sequences serialize only that sequence.
- Parse and deeply compare every result against the intended mutation before accepting it.
- Preserve raw Markdown outside the one intentionally edited rich-text field. Custom HTML/Liquid stays in a source field to avoid destructive conversion.
- Keep existing permalink/layout fields locked in the UI. All new records start unpublished.
- Preview content in a sandboxed opaque-origin iframe with sanitized markup and a nonce-only script policy. It cannot read the editor's GitHub token or local drafts.
- Before publishing, pin the current `main` commit and compare the original file blob SHA. Stale files stop with a conflict. The user can merge non-overlapping fields or export the draft and reconcile manually.
- Create one Git commit containing only the edited file and uniquely named uploaded assets. Update `main` with `force: false`, so a concurrent push rejects the update atomically.
- History loads an older version of just the current file into a draft; the user reviews and publishes it explicitly.

The static preview does not run arbitrary site scripts. Embedded research applications and dynamic filtering should also be checked on the published page. Markdown uses markdown-it for editing previews and Jekyll's Kramdown when published; custom HTML/Liquid is preserved verbatim. Typical paragraphs, headings, lists, images and links share the live templates and CSS.

## Build and verification

`npm ci && npm run build:admin` bundles the editor and a public content/template fallback snapshot. Commit `assets/admin/studio.js` and `assets/admin/context.json` with code/template changes. GitHub Pages serves these directly; it does not require Node at deployment time.

`admin/catalog.json` is generated by Jekyll on every deployment and supplies fresh site/collection context. Opening an editable file reads its current source and SHA from GitHub. A recursive repository tree discovers new records and media, including unpublished content; publication never trusts the bundled snapshot's freshness.

`npm run test:admin` checks every existing content file, all scalar field edits, nested sequence moves, real-template rendering, and optimistic-concurrency publishing. It does not need credentials and never changes public content.
